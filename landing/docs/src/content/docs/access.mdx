Shipper has one workspace. Every account has an immutable user ID, a provisioned email, one role, and one identity across every enabled sign-in method.

There is no public signup, self-invitation, domain-wide admission, or OAuth just-in-time account creation.

## Roles

| Role | Can do |
| --- | --- |
| `admin` | Users, authentication providers, instance policy, connections, updates, recovery, operations tokens, and every application action |
| `developer` | Create and manage applications, deployments, tasks, domains, backup plans, secrets, and terminals |
| `viewer` | Read applications, releases, and activity. No mutation, secret reveal, terminal, backup download, or server setting |

Archive download and restore are admin actions. A developer can create a backup plan and run it but cannot download the archive.

Role checks run on the server after session refresh. Hiding a button is not an authorization boundary.

## Provision an account

Open **Settings → Users** and choose **Add user**.

| Provisioning choice | Result |
| --- | --- |
| Email and temporary password | Stores a password hash and requires a different password before full access. Deliver the temporary password separately. |
| Email with no password | Stores no password credential. Sign-in requires an enabled provider that proves the provisioned email. |

Admins can change a role inline, reset or remove a password, reset a factor, disable or remove an account, and open the per-user audit trail.

The add and reset drawers generate a temporary password locally and show it once. Shipper never stores or returns a readable password.

A temporary-password gate cannot be bypassed by choosing OAuth. Disabling or removing an account denies every login method and revokes sessions and personal access credentials.

The last active administrator cannot be removed, demoted, or left without a working login and recovery route.

## Password sign-in

Email and password is an independent instance toggle in **Settings → Authentication**.

- Passwords are between 12 and 72 UTF-8 bytes.
- An OAuth-only account is not given a password when password login is enabled globally.
- Disabling password login disables it for everyone through ordinary sign-in.
- A temporary password must be replaced before full application access.

Full sessions expire after seven days and are not extended by background traffic. Restricted onboarding sessions expire after ten minutes.

## OAuth providers

Google, GitHub, and Discord are independent toggles. A method must be enabled and usable by the account.

Open **Settings → Authentication**, choose a provider, and enter its client ID and secret. The card shows the exact callback, scopes, setup steps, and a **Test sign-in** action.

| Provider | Callback for `https://shipper.example.com` | Identity scopes |
| --- | --- | --- |
| Google | `https://shipper.example.com/auth/oauth/google/callback` | `openid email profile` |
| GitHub | `https://shipper.example.com/auth/oauth/github/callback` | `read:user user:email` |
| Discord | `https://shipper.example.com/auth/oauth/discord/callback` | `identify email` |

The callback is derived from the canonical HTTPS dashboard origin. If the dashboard domain changes, update every provider callback.

### Google

Create a Web application OAuth client in Google Auth Platform or the Cloud Console. Add the displayed callback to Authorized redirect URIs. Copy the client ID and secret to Shipper.

Shipper validates signature, issuer, audience, expiry, nonce, and verified-email policy server-side.

A Google address can remain marked verified when Google is not its current mailbox authority. If proof is uncertain, establish fresh mailbox control or use an explicit administrator binding.

### GitHub

Create an OAuth App under **Settings → Developer settings → OAuth apps**. Use the dashboard origin as the homepage and the displayed GitHub callback as the authorization callback URL.

Request identity and email access only. Repository permissions are unnecessary for sign-in. GitHub repository access is a separate connection under **Settings → Connections**.

Read verified and private addresses through the authenticated email endpoint, not the public profile email alone.

### Discord

Create or select an application in the Discord Developer Portal, add the displayed callback under OAuth2 Redirects, and copy the client ID and secret.

Use the authorization code flow with `identify email`. Sign-in needs no bot installation, guild, or messaging permissions.

### One identity across providers

A verified provisioned email can link a new provider without creating a duplicate user.

1. Validate the authorization flow and retrieve identity server-side.
2. Resolve an already linked provider's stable user or subject ID.
3. For a new identity, require a verified matching email and exactly one active provisioned account.
4. Complete password-change, enrollment, and 2FA gates before linking.
5. Persist a unique provider and subject binding. Reject collisions and ambiguous mappings without a silent merge.

Changing an email or identity link requires recent authentication, applicable 2FA, and an audit entry.

## Personal TOTP

A user selects **Set up 2FA** under **Settings → Account**.

Shipper generates a random per-user secret and an authenticator QR and manual setup value. The issuer is `Shipper`; the account label includes the email and instance hostname so entries from different servers are distinguishable.

Enrollment remains pending until a correct code is submitted. Only then is the factor active and the recovery codes issued.

- Recovery codes are one-use and consumed atomically.
- After every password or provider sign-in, enrolled users complete Shipper's own second-factor screen.
- A provider's own MFA claim does not skip Shipper's factor.
- There is no remembered-device bypass.
- With enforcement off, a user can disable personal 2FA after recent first- and second-factor verification.
- Replacing a factor or recovery codes requires equivalent protection and invalidates stale challenges.

Store recovery codes offline. Do not keep them in the same password manager entry as the password.

## Require 2FA for the instance

An admin enables **Require 2FA** in **Settings → Access policy**. The policy includes the admin, existing signed-in users without a factor, fresh password accounts, and fresh OAuth-only accounts.

| State | Allowed next action |
| --- | --- |
| Not authenticated | Perform an enabled first-factor flow |
| Temporary password outstanding | Change it in a restricted onboarding session |
| 2FA required without a confirmed factor | Set up and confirm 2FA, sign out, or use defined recovery |
| Confirmed factor needs verification | Submit TOTP or a recovery code |
| All requirements satisfied | Full application access under the account's role |

These are server-side assurance states. Incomplete sessions cannot reach application, configuration, secret, terminal, administration APIs, or ordinary event streams.

Enabling enforcement re-evaluates existing sessions on their next request, so an old cookie or open tab cannot bypass enrollment. Successful enrollment confirmation satisfies the factor for that login.

Personal API tokens cannot bypass required onboarding or enrollment. A token never becomes a human session or an authentication-administration capability.

## Recover access

Try a recovery code first. If that fails:

```sh
# Reset the owner password. Revokes every session.
sudo shipperctl reset-password

# Reset the owner factor. Keeps instance policy.
sudo shipperctl reset-factor

# Claim the instance from the host when no sign-in method works.
sudo shipperctl claim
```

`reset-password` and `reset-factor` are interactive and require a terminal. They stop the control plane, run the recovery command against the data directory, and start the service again.

When 2FA is enforced, a factor reset requires enrollment again. It does not disable the policy for other users.

## Audit and removal

Account and provider changes are audited. The per-user audit trail shows the latest 50 events. Removing a provider also removes its linked identities after the last-admin guard passes.

When an account is disabled or removed:

- Every login method is denied.
- Sessions are revoked.
- Personal operations tokens stop working.
- Terminals opened by that account are revoked.

Running applications are not stopped by an account removal. Workload continuity and human access are separate decisions.

## Common mistakes

- Removing the last administrator.
- Changing the dashboard domain without updating OAuth callbacks.
- Assuming a provider's MFA replaces Shipper's TOTP.
- Sending a temporary password through the same channel as the username without a second factor.
- Leaving a former employee's operations token active after disabling the account.
- Using a viewer account for automation that needs deployment authority.
