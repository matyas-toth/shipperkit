CapRover has been a dependable way to turn a small VPS into a Heroku-like platform for years, and it runs on the same 1 GiB servers Shipper does. The main differences are in what happens around a deploy: Shipper manages databases and backups as first-class parts of an application, and it checks every release before routing traffic to it.

## Choose ShipperKit if

- **Your databases need backups.** Shipper runs native dumps for PostgreSQL, MySQL, MariaDB and MongoDB, and cold archives for other engines and volumes, on a schedule, locally and to S3. Restores always create a copy.
- **You don't want a wildcard domain.** Each application gets the domains you give it, with HTTPS issued and renewed automatically.
- **You want Compose files that build.** Shipper builds Compose services from source and finishes every build before it updates the running stack.
- **Releases have to fail safely.** A failed health check never takes traffic, and every release records what actually ran.
- **You need teammates.** Admin, Developer and Viewer roles, Google, GitHub and Discord sign-in, and two-factor authentication are built in.

## Choose CapRover if

- **You want to add worker nodes** to a Docker Swarm cluster.
- **You prefer nginx** and want to edit its configuration template directly.
- **You already have captain-definition files** and a workflow built around them.

## Moving from CapRover

Apps with a Dockerfile move as they are. Point Shipper at the same repository, deploy, restore your database dumps as new databases, and switch DNS when each app checks out. The [move an existing app](/docs/move-an-app/) guide walks through the order.
